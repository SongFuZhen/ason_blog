要把模型跑起来，第一个要选的，是拿什么跑。

我选了 Ollama。

原因很简单：它把「在本地跑一个大模型」这件听起来很吓人的事，压成了一条命令。

`ollama pull ornith:9b` 是把模型下载下来。

`ollama run ornith:9b` 是直接开聊。

`ollama list` 是看看自己装了哪几个。

它背后是一个本地推理运行时，前面再挡一个兼容 OpenAI 的接口（11434 端口上的 `/v1`），所以你以前调 GPT 的代码，把地址指过来就能用。

Windows、macOS、Linux 都行，关键是——它能在纯 CPU 上跑。

这在后面讲量化时会明白为什么重要。

### 把 Ollama 塞进 Docker

GraphMap 没有在宿主机直接装 Ollama，而是给它单独打了个镜像。

这里先补一个最基础的概念：镜像和容器不是一回事。

镜像像一张安装盘，是静态的模板。

容器是这张盘「装好并开机」之后的那个活实例。

你 `docker run` 一次，就从一个镜像生出一只容器；容器删了，只要镜像还在，随时能再起一只。

GraphMap 的 Ollama 编排长这样（精简过）：

```yaml
ollama:
  image: graphmap-ollama:1.0.0-x86
  network_mode: host
  volumes:
    - /opt/graphmap/models:/root/.ollama
  environment:
    - OLLAMA_HOST=0.0.0.0:11434
    - OLLAMA_ORIGINS=*
```

几个点值得停一下：

`network_mode: host` 让容器直接用宿主机的网络，Ollama 监听 `0.0.0.0:11434`，端口和配置都不变，外面连起来最省心。

`volumes` 把宿主的 `/opt/graphmap/models` 挂到容器里的 `/root/.ollama`——模型存到了磁盘上。

这意味着容器删了、重建了，你拉过的模型还在，不用重新下载。

`OLLAMA_ORIGINS=*` 是放开跨域，方便网页前端直接调它。

应用容器这边，只通过一个环境变量指过去：

```
OLLAMA_HOST=host.docker.internal:11434
EMBED_MODEL=nomic-embed-text
CHAT_MODEL=ornith:9b
```

这里正好对上 RAG 的两个活儿：`nomic-embed-text` 管 embedding（默默把文档压成向量），`ornith:9b` 管 generation（开口回答）。

### 9B 模型凭什么在 CPU 上跑

这是个绕不过去的问题。

ornith:9b，「9b」是 90 亿参数。

模型说到底就是一大堆浮点数（权重）。

如果全用 FP16（半精度）存，一个参数 2 字节，90 亿个就是差不多 18GB——光装进内存就够喝一壶，更别提 CPU 一点点算了。

所以本地能跑，靠的是量化。

量化的意思，是把这些高精度的权重「压缩」成低精度。

比如压到 4-bit，体积直接砍到约四分之一，算起来也轻得多。

代价是精度有损，回答偶尔会糙一点、会漏点细节。

但换来的，是一张普通办公机、甚至一块树莓派级别的硬件就能跑起来。

Ollama 里模型的载体叫 GGUF，这文件里就是量化后的权重加一份配置。

你看到的 `q4_K_M` 这类名字，末尾那段就是在说「用什么档位量化」。

GraphMap 的 `.env` 里还留了更小的选项，比如 `qwen2.5:0.5b`（5 亿参数，更轻）。

它的部署文档里甚至写了按内存自动选模型：机器 ≥32G 就上 7b，内存低于 16G 就退到 3b。

这就是量化最现实的好处——同样的活，看菜吃饭。

### 断网环境：整套带走

回到 GraphMap 那个卖点：目标机没外网。

那模型从哪来？

做法是先在**有网**的机器上 `ollama pull` 好，再把模型目录 `tar` 成一个包。

U 盘拷过去，在目标机上解压到 models 目录，重启 Ollama 容器即可。

镜像本身也一样：联网机 `docker save` 导出成 tar，目标机 `docker load -i` 导入。

GraphMap 那套交付，就是这么「U 盘带走」的——上海服务器那个 3.5GB 的压缩包，整整齐齐。

甚至连 Docker 本身都能离线装（它随附了一份离线安装包）。

所以从拉模型、打镜像、到搬上断网的目标机，是一条闭环。
