上篇单机跑通了。

但生产环境不能只有一台。

最朴素的担心：那台机器重启、死机、拔错网线，RAG 就整个瘫了。

我要的其实是「挂一台，没事」。

这就是 Ollama-HA 要解决的问题。

### 把三台拼成「一台」

Ollama-HA 的思路不复杂：找三台同构服务器，每台都跑好 Ollama，然后在外面罩一层网关，让它们对外看起来像一台。

里面是四个 IP：

- 三台节点 `10.10.10.11 / .12 / .13`，各跑 Ollama（端口 11434）。
- 一个 VIP `10.10.10.100`，是外界唯一要记住的地址。

客户端永远只打 VIP:11435，不知道背后有几台、谁在职。

### 负载均衡：谁闲谁接

网关里是 Nginx，策略叫 `least_conn`——新请求分给「当前连接数最少」的节点。

这比轮询聪明一点：某台正在扛重活，就少分点给它。

某台 Ollama 连续失败 3 次，会被摘出池子，15 秒后再探一次。

所以一台慢了、挂了，流量自动绕开，你这边最多感觉到某次请求慢一点。

### VIP 漂移：整机挂了也不慌

光有负载均衡还不够——万一是整机宕了呢？

那台没了，它身上的 VIP 也得跟着走。

这里用 keepalived + VRRP：三台互相发心跳（协议号 112，不是端口），谁活着、优先级高（150/140/130），VIP 就停在谁身上。

某台整机出不了网，心跳丢了 3 次，VIP 秒级漂到下一台健康节点。

客户端还在打 `10.10.10.100:11435`，毫无感觉。

还有个细节叫 `nopreempt`：坏机器修好回来，VIP 不主动回切，避免两台来回抢导致抖动。

新主当得好好的，就让它继续当。

### 入口要上锁，大屏要能看

11435 这个入口是要带 Key 的（`Authorization: Bearer <key>`，nginx 纯字符串比对）。

而 Ollama 本体 11434 本身没鉴权，所以只对内网、只给三台互联用，不对外。

另外有个运维大屏 `18000/ha/`：三台节点的 CPU、内存、磁盘、GPU（逐卡）、Ollama 状态、告警，一眼全绿才算健康。

部署本身也照顾了断网场景：U 盘把整个包拷过去，每台跑一条 `install.sh --vip ... --nodes ... --key ...` 就完事，脚本幂等，跑几遍都安全。

镜像是在办公机的 WSL 里提前 `build-image.sh` 打好的。

### 现在说说 event loop

话题转到另一个词：event loop（事件循环）。

你用任何聊天模型时，字是一个一个蹦出来的，不是憋半天吐一整段。

这背后有两层「循环」。

第一层是生成循环。

大模型不是一次性算出整段话的。

它是循环：拿着已有的文本，预测「下一个最可能的词（token）」，接上去，再预测下一个，如此往复，直到遇到结束符。

每一步都在「想」，每一步也都产出一点点。

第二层是流式推送。

服务器用 SSE（Server-Sent Events）把这一个个 token 当作事件，边产生边往浏览器推（一种 `text/event-stream` 的流）。

浏览器收到一个事件就渲染一行，于是你看到字逐个出现。

这么做不只是好看——首字出来的快，长文本也不用等全部生成完才给你看。

那服务端为什么能同时伺候这么多路「边想边吐」的会话？

靠的就是 event loop，或等价的并发模型。

Ollama 是 Go 写的，用 goroutine；很多别的推理服务用 Python 的 asyncio，或者 Node 的事件循环。

名字不同，干的活一样：非阻塞 I/O + 一个调度核心，让一个进程能同时「挂着」成百上千路流式连接——A 在等 token、B 也在等，调度核心在它们之间切换，谁有数据就推谁。

没有这层，就得给每个会话开一个线程，并发一高内存就爆、调度就垮。

### 高可用遇上端流，更挑剔

把两件事放一起看更有意思。

nginx 把一路 SSE 流代理到某节点，节点用事件循环处理；节点挂了，nginx 摘它、VIP 漂走。

但那条正在吐的流会断。

所以长连接流式比普通请求更怕抖动——客户端得会重连、会重试，高可用方案也得对「流」更上心。

这也是为什么 HA 里要对坏节点快速摘除、对冷启动（模型还没加载完，偶发 502）提前预热。
